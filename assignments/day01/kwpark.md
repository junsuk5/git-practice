### 1. 오늘 내가 직접 손으로 치며 배운 점 ###

Git은 단순히 파일을 백업하는 프로그램이 아니라, 파일의 변경 이력을 저장하고 원하는 시점으로 돌아갈 수 있게 해주는 
버전 관리 도구라는 것을 다시 확인했다.
Working Tree → Staging Area → Repository로 이어지는 Git의 3대 영역을 직접 명령어로 확인하면서 각각의 역할을
 구분할 수 있게 되었다.
- git status를 통해 현재 파일이 수정됨 / 추적되지 않음 / 스테이징됨 등의 상태를 확인하는 습관이 중요하다는 것을 알게 되었다.
- git add는 단순히 파일을 저장하는 명령이 아니라, 이번 커밋에 포함시킬 변경사항을 장바구니에 담는 과정이라는 것을 이해했다.
- git commit을 통해 현재 작업 상태를 하나의 버전으로 확정하고, git log를 이용해 과거 작업 이력을 확인할 수 있다는 것을 배웠다.
- GitHub의 원격 저장소와 로컬 저장소를 연결하고 push, pull, clone을 이용해 서로의 작업 내용을 주고받는 기본 흐름을 이해했다.
특히 Branch는 모듈을 나누는 것이라기보다 하나의 프로젝트에서 기존 작업을 안전하게 유지하면서 별도의 작업 흐름을
만드는 것이라는 점을 이해했다.
작업 브랜치에서 작업한 내용을 Pull Request(PR)로 올리면 다른 사람이 검토한 후 main/master 브랜치에 합칠 수 있다는 
협업 과정을 배웠다.

### 2. 가장 멘붕이었던 순간 & 트러블슈팅 ###

문제 상황: Git에서 파일을 수정한 것과 git add.를 한 것, 그리고 git commit한 것의 차이가 처음에는 헷갈렸다.
원인: 모두 "저장"하는 것처럼 보이지만 실제로는 각각 다른 공간과 역할을 가지고 있기 때문이다.

해결 방법:
-git status → 현재 내 작업 상태 확인
-git add → 커밋할 변경사항을 Staging Area에 올리기
-git commit → 변경사항을 하나의 버전으로 확정
-git log → 확정된 버전들의 기록 확인
직접 명령어를 반복해서 실행해 보니 "수정 → 장바구니에 담기 → 세이브"​라는 흐름으로 이해할 수 있었다.
특히 Git에서는 문제가 발생했을 때 무작정 파일을 삭제하기보다 현재 상태를 먼저 git status로 확인하는 것이
중요하다는 것을 배웠다.

### 3. 나만의 언어로 재해석한 핵심 용어 사전 ###

💡 Git 명령어를 외우는 것보다 각각의 역할을 하나의 작업 흐름으로 이해하는 것이 중요했다.

- Working Tree: 내가 지금 실제로 작업하고 있는 책상. 파일을 만들고 수정하는 공간이다.
- Staging Area: 오늘 제출할 물건을 미리 담아놓는 장바구니. git add를 하면 이곳에 들어간다.
- Repository: 확정된 세이브 파일을 보관하는 나만의 게임 저장소. git commit을 하면 기록으로 남는다.
- git status: "지금 내 책상과 장바구니에 뭐가 있는지 보여줘!"라고 확인하는 상태 점검 명령어.
- git add: "이 파일은 이번 세이브에 포함할게."라고 장바구니에 담는 행동.
- git commit: "여기까지 작업한 것은 하나의 버전으로 확정!"이라고 저장 버튼을 누르는 것.
- Branch: 같은 프로젝트에서 원래 작업을 건드리지 않고 옆에서 새로운 작업을 해볼 수 있는 별도의 작업 레일이다.
- Merge: 별도의 작업 레일에서 완성한 결과물을 원래 레일에 합치는 것.
- Pull Request(PR): "제가 별도 브랜치에서 작업을 끝냈습니다. 한번 검토해 보시고 원래 프로젝트에 합쳐주세요.
"라고 보내는 공식 검토 요청이다.
-GitHub: 내 컴퓨터에 있는 Git 저장소를 인터넷에 올려놓고 다른 사람과 함께 작업할 수 있는 온라인 협업 공간이다.

### 4. 오늘 배운 내용을 한 문장으로 정리 ###

git은 단순한 백업 도구가 아니라, 내 작업을 안전하게 기록하고 Branch와 PR을 이용해 다른 사람과 함께 개발하기 위한 
협업 시스템이다.
오늘 가장 크게 이해한 것은 "브랜치를 왜 사용하는가?"​이다.
기존 코드를 바로 수정하는 것이 아니라,브랜치 생성 → 작업 → 커밋 → Push → Pull Request → 검토 → Merge
라는 흐름으로 작업하면 기존 프로젝트를 안전하게 보호하면서 새로운 기능을 개발할 수 있다.
앞으로 OpenCode를 이용해 웹앱을 개발할 때도 기능별 또는 목적별로 브랜치를 만들어 작업하고, 완성된 내용을 검토한 후 
메인 브랜치에 반영하는 방식으로 활용해야겠다.
